# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Converts a boat's lines plan "table of offsets" (CSV, values in feet-inches-eighths such as `1-10-2`) into DXF drawings using `ezdxf`. Core library is the single module `table_of_offsets.py`; per-project scripts live in `tutorial/`.

## Commands

    python3 -m venv ~/.venvs/off2dxf && source ~/.venvs/off2dxf/bin/activate
    pip3 install -r requirements.txt        # numpy, pandas, ezdxf, black

    python -m unittest discover -v -s ./tests -p "test_*.py"     # all tests (same args as .vscode/settings.json)
    python -m unittest discover -s ./tests -p "test_*.py" -k offset2double   # single test by name

    black .                                  # formatter (format-on-save in VS Code)

Tutorial scripts (e.g. `tutorial/project89.py`) are run directly and write `.dxf` files into `./out` in the current directory (git-ignored; `--out-dir DIR` to change, see `table_of_offsets.output_dir_from_args`; `DXF.close` creates the directory). The coordinates in the .dxf are in `Model.output_unit()` (default the unit of the table, "inch" for `ftin`; `--output-units` / `set_output_unit`); `Model.open_dxf(file)` makes a `DXF(file, unit=output, source_unit=Model.units())` that scales the coordinates and the text heights from the unit of the model and sets `$INSUNITS` and `$MEASUREMENT` (0 for inch/ft, 1 for the metric units).

## Units

The unit of the table is never guessed: it is `Model(csv, unit=...)` or `[table] unit` of the meta data file (they must agree), else ValueError. The model works in that unit (`Model.units()`); nothing is converted to inches. The exception is `ftin`, a notation (`2-3-4`) and not a unit: its cells are converted to inches (`offset2double`), so a `ftin` model works in inches (there is no feet output unit). Meta data lengths are not converted. Sizes of the drawing furniture (margins, text heights, label offsets, defaults of `gap`) are given in inches and converted by `Model.inches(x)`; `DXF.text` has a default height of one inch of the source unit. The default station spacing (12) exists only for `ftin` (a foot); other units need `spacing` or `positions` in `[stations]`.

## Architecture

- `TableOfOffsets.offset2double` parses `F-I-E` strings to inches. Trailing `+`/`-` means +/- 1/16". Missing parts are allowed (`1-0`, `3`). A cell `straight` (`STRAIGHT_LINE_MARKER`, "STRAIGHT LINE" in the books) is replaced at load time (`Model._resolve_straight_lines`) with the value on the straight line between the nearest values of its row to the left and right, interpolated by `station_positions()` (so the grid must give the right positions) and written in the unit of the table (`length_to_offset`; `ftin` is rounded to 1/16"); a run needs a value right before and after it (ValueError). A cell with two values (`0-2-0 and 0-3-0`) is malformed unless `Model.set_multi_value_policy("first")` (see `MULTI_VALUE_POLICIES`) is set: then the first value is used; project 89 sets it.
- `Model` wraps a pandas DataFrame read from the CSV (cells kept as text; `Model(csv, unit=...)` with `unit` one of `TableOfOffsets.UNITS`, e.g. `"ftin"` or `"mm"`; `offset_to_length` parses them, see Units). First column `#` is the line name (Sheer, `B 3'`, ...); other columns are station numbers. Station x-position: see Meta data (default for `ftin`: the n-th column at `n * 12` inches; other units need `spacing`). It is a base class: subclasses override the "(virtual)" methods (`waterlines_positions`, `buttocks_positions`, `base_offset`, `grid_y_origins`, `drawing_area_vertical_borders`, `breadth_line_to_index`, `height_line_to_index`). `set_under_waterline` marks stations where a line's offsets are negated (see `offset_sign`).
- `DXF` is a context manager around an `ezdxf` R2010 doc with layers `grid`, `red`, `text` and `extra_points` (`EXTRA_POINT_LAYER`: the circles and the labels of the extra points; `DXF.add_circle(..., layer=)`, `DXF.text(..., layer=)`). It saves on exit. Note that `__exit__` re-raises as a bare `Exception` and returns True.
- `tutorial/projectNN.py` / `projectbluemoon.py` each subclass `Model` for one boat's CSV, then plot the grid and lofted lines. `tutorial/context.py` and `tests/context.py` put the repo root on `sys.path` so `import table_of_offsets` works; scripts and tests import via `from context import ...`.

## Meta data (grid)

`Model(csv, unit=None, meta=None)` loads a TOML file next to the CSV with the extension `.meta` or `.grid` (synonyms; `find_meta`, both existing is a ValueError; `meta=PATH` to give one, `meta=False` for none) via `load_meta`, which rejects unknown sections/keys and malformed values (ValueError). Sections: `[table]` (`unit`, `bow_station`, `multi_value`, `dwl`: the height of the design waterline above the base line, `Model.dwl()`, None if not given; `ProjectBlueMoon` takes the base of its `LWL to ...` rows from it), `[stations]` (the station names are just labels - `"1"`, `"T"`, `"AP"`, `"FP"`, `"1A"`; the position of a station comes from its place in the list of the CSV columns: x = `origin` (default 0) + n * `spacing` (default 12 for `ftin` only, may be negative); `positions = {FP = 3000, "1A" = 2500}` gives x by name for tables whose stations are not equally spaced; a station without a position is a ValueError), `[transom]` (a raked transom: `station` = the column of the table, `extra_points` = exactly two points, written like those of `[rabbet]` (`station`, `dx`, `dy`, `height` / `height_row`; no `breadth`, `edge`), that are two points of the transom line in the profile view (`transom_line()`, different heights); `loft_line_n` puts the points of that column on the line at their height (`point_x`: a profile row at its own y, a plan row at the height of the waterline or of the `body_points` item with that half-breadth row; else at the station position); `plot_transom_line(dxf)` joins the points of the column in the profile view (`transom_profile_line()`) and in the plan view (`transom_plan_line()`); `plot_sheer_end_lines(dxf)` joins the two ends of the sheer line of the plan view (the first `body_points` item) to the plan centerline (`sheer_end_plan_lines()`); the keel line, `keel_point_at`, the diagonals and the body plan do not use the transom line yet), `[waterlines]` (`{height, row}`; `height` above the base line, or `dy` above `dwl` of `[table]`: `LWL = { dy = 0.0 }`), `[buttocks]`, `[diagonals]` (`{row, from = [0, y0], through = [x1, y1]}`; a point may also be `{ x = N, dy = N }` (`x` default 0), `dy` above `dwl` of `[table]`: `from = { dy = 0.0 }`), `[keel]` (`height_row` / `breadth_row`, optional, like those of `[rabbet]`: the table row with the heights of the keel (e.g. `Profile`) and the row with its half-breadths; `from`/`to` = `{ station, height }`: the straight keel line of the profile view, `Model.keel_line()`; `siding`: the breadth of the keel across the centerline, `Model.siding("keel")`, its half is the half-breadth) `[chine]` (`height_row` and `breadth_row` of the chine, a hard chine hull: `chine_body_point()`; `loft_body_lines` adds it to the body lines and joins the chine points of the consecutive stations into `BodyLines.chine`, drawn by `plot_body_lines`, `chine=False` to omit) and `[rabbet]` (`height_row`: the table row with its heights; `breadth_row`: the row with its half-breadths, optional; `extra_points` (not rabbet specific: a generic way to add geometry that is not in the table, e.g. a keel or the shape of a stem; the sections of `EXTRA_POINT_SECTIONS`, now `[rabbet]` and `[keel]`; `Model.extra_points(section)`): points of the element, an optional boolean `edge` (default false; `Model.extra_point_edges(section)`) marks a sharp corner of the line: the point is seen in the profile view, its edge, the line across the breadth of the element, is drawn in the plan view (`edge_plan_lines()`, from the plan centerline to the half-breadth) and in the body plan (`BodyLines.edges`, at the height of the point; `edges=False` to omit in `plot_keel_and_rabbet` and `plot_body_lines`), `[{ station, dx, dy, height, breadth }, ...]` = the XY (profile view) coordinates, `dx` (default 0) to the right of the station, `height` above the datum and `dy` (default 0, optional; also with `height_row`) added to the height, and the optional half-breadth `breadth` (default: that of the rabbet at the nearest x); `height_row` / `breadth_row` instead of the numbers take the values of table rows at the station (the same as the sheer point); a `height_row` that is the name of a waterline is the height of that waterline, not the row of the same name, which holds half-breadths; for the rabbet they are merged in x order into the line of the table (`rabbet_profile_line()`, `rabbet_plan_line()`); for the keel they are merged by x with the row `height_row` of `[keel]` and the `from`/`to` line if there are any (`keel_points()`: the half-breadth of a row point is that of `breadth_row` at the same x, else the nearest one, else half of `siding`; without a row and a line the extra points are in the order of the file; `keel_point_at(station)` interpolates along it, a section goes down to it, `siding` of `[keel]` is the default breadth); they also take part, as pseudo stations at their x (the side is chosen like that of a station), in the line of the element in the body plan (`BodyLines.extra_points` has their body plan coordinates with the label); `plot_keel_and_rabbet` and `plot_body_lines` mark them with a circle and the label `E1`, `E2`, ... (rabbet) or `K1`, ... (keel) (`extra_points=False` to omit); `siding`: used when there is no `breadth_row`, the half-breadth is half of it; the base class gives `rabbet_body_point()` = (`breadth_row` or half siding, `height_row`), `loft_body_lines` adds it to the body lines; the Tabby Cat and project 89 models still override it), `[ghost_line]` (`row`, `height`), `[sheet]` (`y_origins`, `vertical_borders`) and `[patches]` (corrections of cells of the table, the CSV is kept as it is: `"Row name" = [{ station, value, was, note }, ...]`, `value` written like a cell, `was` (optional) must be the cell of the CSV, else ValueError, so a patch of a changed table fails; applied at load time before the straight lines, `Model.patches()` lists them, `diagonal_check_report` marks them). `Model.plot_keel_and_rabbet(dxf)` draws the keel and rabbet lines of the profile and plan views from `[keel]` and `[rabbet]` (`keel_profile_line`, `rabbet_profile_line`, `keel_plan_line`, `rabbet_plan_line`; the plan centerline is `plan_centerline_y()`, the second `y_origins`), so a project does not draw them. Lengths are in the unit of the table (`[table] unit`: inches for `ftin`, millimetres for `mm`, ...) and are not converted. The base-class "(virtual)" methods return these values, so a subclass overrides only what the file cannot say; a subclass override wins. `sample_data/offset_table.meta` is the file for project 89 (which no longer overrides the grid methods); `sample_data_too/offset_table_blue_moon.meta` is that of Blue Moon (no diagonals: their lines are not known; the keel has an extra point); Tabby Cat and the ferrocement hull still hard-code theirs. Not in the file yet: `base_offset` rows, `set_under_waterline`, keel/rabbet body points.

## Body plan

`loft_body_line(station, [(breadth, height), ...])` builds one body line; each item is a table row name or a number in the unit of the model. `breadth_at` / `height_at` look rows up by name (`breadth_line_to_index` / `height_line_to_index` are overridable). `breadth_at` ignores `base_offset` (sheet placement is vertical only). `ProjectBlueMoon.body_lines()` is the reference example; Options: `placement` (`"max_breadth"` default = centerline on the widest station, `"right"` = clear of the profile view, `"raw"`) and `sides` (`"half"`, `"both"`, `"split"` = aft stations left, forward right; default `"split"` for `"max_breadth"`, `"half"` otherwise, see `body_plan_sides`; the bow end comes from `set_bow_station(station)` / the `bow_station` argument, default the greater x). Both projects now produce body lines. Diagonals: the overridable `diagonals_positions()` gives `{name: (y0, x1, y1)}` (the unit of the model, heights above the base line; the line from `(0, y0)` through `(x1, y1)`), the table row (`diagonal_row(name)`, default the name) holds the distance along it from `(0, y0)` to the hull. `loft_body_lines` adds the hull points of the diagonals that are in the table (`diagonal_body_points()`, `DiagonalPoint` items of `body_points`) like the waterlines, and the diagonals are drawn in the grid (`diagonal_segments`). `plot_waterline_plan_labels(dxf)` labels the waterline lines of the plan view (the rows of `waterline_row(name)`) with the waterline name just beyond their end with the greatest x (Blue Moon calls it). In the plan view the diagonals are drawn below the plan centerline, opposite to the waterlines and the sheer (`loft_diagonal_plan_lines`, `plot_diagonal_plan_lines`, used by `ProjectTabbyCat.save_model_as`). The definitions are data that must be given (read from the drawing or provided), not guessed or fitted: the Tabby Cat model has them from the dimensions of `konstruktivnyy_midel-shpangout_2.jpg` (`DIAGONALS_MM`). The lowest point of every body line (the keel) is joined to the centerline by a horizontal segment (`keel_link=True`, `loft_body_lines`). The first of the `body_points` is the sheer: `loft_body_lines` returns a `BodyLines` (a dict with the attribute `sheer`, see `body_sheer_polylines(lines)`) whose sheer line joins the sheer points of the consecutive stations, one polyline per side; stations whose sheer cell is empty are skipped, not extrapolated (see the TODO). The rabbet line (`BodyLines.rabbet`, `body_rabbet_polylines`) is made the same way from the point of the overridable `rabbet_body_point()` (default `None` = no rabbet line; the Tabby Cat, Blue Moon and project 89 models override it; the ferrocement hull has no rabbet). The keel line (`BodyLines.keel`, `body_keel_polylines`, `keel_body_point()`; all four projects override it, project 89 uses `Profile Plan`/`Profile`) is a separate thing from the keel link (the lowest point joined to the centerline). With `placement="right"`, `body_plan_grid_options()` gives `plot_grid` the extension of the base line (first `grid_y_origins`) and waterlines plus a vertical body plan centerline and the buttock lines (`buttocks_positions`). `loft_body_lines` always adds the waterlines of `waterlines_positions()` that have a half-breadth row in the table (`waterline_body_points()`, row name from the overridable `waterline_row(name)`), so projects list only the other points; it returns `{station: [polyline, ...]}`; `body_polylines()` flattens it. `plot_annotated_body_line(dxf, station, body_points)` (used by `ProjectFerrocement.save_station_as`) draws one station with every point labelled with the table rows its coordinates come from, plus the base line (y = 0), the waterlines and the buttocks, for checking odd body lines. `plot_body_lines(dxf, lines)` draws them with the station name above the top end of each, and the sheer, rabbet and keel lines (`sheer=False`, `rabbet=False`, `keel=False` to omit; the tutorial scripts use it). `plot_body_plan_grid(dxf, lines)` draws the grid (base line, waterlines, `CL`, buttocks) of a body plan alone; the `save_body_lines_as` methods (the `*_body.dxf` files) draw it under the body lines.

## Data

`sample_data/` holds the primary CSV and `a_ferrocement_hull/` (a table in millimetres transcribed from an FAO drawing, with the source images; see `tutorial/project_ferrocement.py`) and `tabby_cat/` (a table in millimetres transcribed from a lines plan picture; waterline heights given by the user, buttocks 300 mm and stations 510 mm apart, confirmed by the user; see `tutorial/project_tabby_cat.py`). `sample_data_too/` is a git submodule (`git@github.com:yyk99/tables_of_offsets.git`) with more tables (`offset_table_181.csv`, `offset_table_blue_moon.csv`). Run `git submodule update --init` to fetch it.
